# MIG-01. Проверка группового разговора

Групповой replay задаёт одну последовательность сообщений и событий для сравнения двух версий приложения. Базой служит действующий движок v0.2. Для оценки меняют одну вещь за раз: сначала реализацию сценария на прежних весах, затем отдельно веса. Синтетические истории для проверки поведения хранятся отдельно от закрытых диалогов для человеческой оценки юмора.

## Как повторить

Из корня checkout выполните команды с новыми именами выходных файлов. В первом запуске генератор отвечает фиксированной фразой. Второй использует единственный inference slot локального llama.cpp и проверяет доступность модели. Флаг `--port` переопределяет порт 18080. Для проверки требуется свободная модель.

```powershell
uv run pozor eval replay --output data/mig-01/fixture.json
uv run pozor eval replay --live --output data/mig-01/qwen.json
```

Временная база создаётся заново для каждого сценария. Фикстура поступает через durable inbox, команды и очередь приложения. Эмулятор Telegram записывает попытки, уведомления и подтверждения. Участники явно включены по правилам v0.2. Указанные в сценарии моменты доставки отделяют подготовку черновика от попытки отправки. Следующее входящее событие подаётся по завершении генерации предыдущего. Инвалидацию во время работы модели дополнительно проверяет `test_new_reply_during_inference_replaces_revision` в [тестах доставки](../tests/test_delivery.py).

## Решения владельца от 20 ноября 2026 года

- В целевой беседе нет раундов. Удалить `/finish`. Автор может отменить ожидающий ответ командой `/stop` в reply на свой вопрос. Без reply команда отменяет его последнее ожидающее задание в текущей теме. Администратор может отменить выбранное задание. Уже отправленное сообщение остаётся отправленным; исход неоднозначной попытки сохраняется.
- При исключении участника скрывать прежние данные из контекста и памяти. После возврата снова доступны только сохранившиеся данные, на которые продолжают действовать права и срок хранения. Поступившее за время исключения не собирается. Удаление данных остаётся отдельной операцией.
- В первом офлайн-эксперименте проверять максимум одну инициативную реплику за 10 минут на тему. Прямые обращения обслуживаются независимо. Момент для вступления по-прежнему требует свежего человеческого сообщения. По решению владельца пороги выбирают после замеров на разработочных примерах и утверждают до вскрытия отдельной контрольной выборки. Дедлайны и debounce нового движка измеряются в MIG-06 на разработочных сценариях.

## Результаты MIG-01 и MIG-02

Исходный replay в коммите `b733620` зафиксировал поведение v0.2. До и после выделения обработчиков выполнены семь одинаковых сценариев с фиксированным генератором и с Qwen3-8B Q4_K_M. Проверены SHA-256 файла модели и сервера llama.cpp, сборка 11718, commit 547208dca. В [отчёте](../reports/mig-01-02-replay.json) сохранены настройки, отпечатки исходников и набора, результаты доставки и задержки генерации.

| Сценарий | Наблюдение до и после |
|---|---|
| Две ветки в одной группе | Из трёх ожидаемых ответов отправлен один — на сообщение №6. На №5 черновик подготовлен, но до публикации вытеснен следующим обращением. Реплика №7 осталась без ответа. |
| Вопросы в двух форумных темах | Обе отправки дошли. Ответ на №3 остался в теме 101, ответ на №4 — в теме 202. |
| Редактирование, отзыв согласия, удаление и рестарт до отправки | Во всех четырёх сценариях подготовленный текст не ушёл. При удалении очищены связанные ходы. |
| Неоднозначный результат доставки | Одна попытка. После перезапуска сохранено состояние `unknown`. |

С фиксированным генератором совпали все результаты сценариев, кроме длительностей. На Qwen совпали наборы адресатов, попытки, уведомления, исходы и ошибки. Девять вызовов генератора в каждом прогоне дали ответы без fallback. В семи позициях с синтетической меткой «промолчать» вмешательств не наблюдалось. Отдельное ожидание очереди в этом групповом replay не измерялось. Вариативный текст и небольшое число генераций ограничивают выводы о качестве и скорости.

MIG-02 переносит управление заданиями в `app/delivery.py`. Правила продолжения, генерация и отправка выделены в `core/usecases`. SQL-переходы и транзакции остаются в `infra/sqlite`. При одновременном удалении хода и HTTP 429 обработчик теперь завершает попытку без повтора и исключения. Этот случай дополнительно воспроизведён на временной БД.

## Что измерять

| Вопрос | Наблюдаемая величина |
|---|---|
| Ответил ли бот на прямое обращение? | Для каждого ожидаемого ответа сверить факт доставки, чат, тему и ID сообщения, на которое ответил бот. Два одновременных обращения дают две возможности ответить. |
| Стоило ли вступать? | Для инициативы отдельно посчитать долю вмешательств среди случаев с меткой «промолчать» и долю пропущенных поводов среди случаев «ответить». Недостаточно данных для знаменателя — результат не определён. Запасная реплика и опубликованное уведомление тоже попадают в подсчёт фактических вмешательств. |
| Попал ли ответ по адресу? | Проверить reply-to и отдельно названного в тексте человека. Верный ID в Telegram ещё не гарантирует верной адресации текста. Записывать лишние отправки и ошибки на уровне каждого случая. |
| Сколько пришлось ждать? | Отдельно время генерации, ожидание очереди и полное время от приёма до попытки доставки. Замеры приводить с числом наблюдений и режимом модели. Движение тестовых часов и задержку эмулятора транспорта не интерпретировать как скорость Telegram. |
| Что произошло при отмене? | Посчитать отменённые задания, публикации после инвалидации, повторные попытки после неоднозначного исхода. После удаления зависимого источника редактируемые тексты и сброшенные черновики не должны попасть в отправку или память. |
| Хорош ли текст? | Отдельная человеческая оценка контекста, ясности, юмора и повтора. При сравнении версий засчитывать победы среди всех оценённых пар, включая ничьи в знаменатель. Условия HUM-01 — от 40 слепых пар и 60% побед. |

Синтетическая метка отражает намерение автора сценария. Перед оценкой инициативы на человеческих примерах фиксируют метки и критерии. Для сравнения версий сохраняют входы, времена и порядок событий, версию исходников, настройки, модель и шаблон. Точные совпадения случайно сгенерированных фраз не требуются.

## Контракт целевого движка для следующих этапов

| Объект | Обязательные различия и связи |
|---|---|
| Событие | Ключ сообщения включает scope чата/темы, пространство источника и ID сообщения. Событие несёт тип, автора, время, ссылку на родителя, версию или хеш. Отсутствующий родитель явно помечен. Повтор события идемпотентен. |
| Контекст | Опорные сообщения задания, доступная ветка reply, недавние реплики, подтверждённые ответы бота, разрешённые адресаты и доступные источники памяти. У каждого исходного сообщения свой автор. В обычной группе reply не создаёт новую тему. |
| Задание | Независимый `response_id`, причина `direct` или `initiative`, scope, опорные сообщения, revision, снимок прав, зависимости от источников, время создания и deadline. Параллельные прямые обращения получают отдельные ID. |
| Решение | `speak` содержит текст, допустимый reply-to и необязательных адресатов. Для инициативы допустим `skip`, который завершает задание без outbox. Невалидный адресат или источник не даёт полномочий на отправку. |
| Память | Для записи нужны тип, scope, ссылки на источники с их версиями и правами, необязательные субъекты сведений. Проверка зависит от автора текста и того, о ком он написан. Собственную подтверждённую шутку бот может использовать для связи разговора и защиты от повтора. |
| Доставка | Один outbox на конкретный ответ с состоянием и подтверждённым ID Telegram при успехе. Последняя проверка прав, revision и срока совмещена с переходом в `sending`. Вызов транспорта следует сразу после фиксации транзакции. |

Для нового задания основной путь — `pending → queued → generating → ready → sending → sent`. Решение промолчать завершает генерацию в `skipped`. Отмена до отправки даёт `cancelled`, ошибка подготовки — `failed`. Ответ 429 возвращает попытку в ожидание с повторной проверкой, 403 отключает чат. После неоднозначной отправки или рестарта из `sending` результат — `unknown`. Очередной вопрос другого человека не делает прямое задание устаревшим. Изменение использованного источника, отмена задания или изменение его прав требуют повторной проверки.

Эти контракты определяют последующие MIG-этапы. В исходном движке действуют сессии, согласие и лимит ходов.
